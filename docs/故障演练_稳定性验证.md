# Krpc 故障演练与稳定性验证手册

> 目的：用**几组固定步骤**，证明 Krpc 在常见故障场景下的行为是可预期的，而不是“刚好没挂”。所有命令均假设在仓库根目录 `/home/zzz/Krpc` 执行。

---

## 1. ZK 发现 + 多实例 + 宕机切换

### 1.1 场景目标

- 同一 RPC 方法在 ZooKeeper 下注册 **多个实例**（如 8000 / 8001）。  
- 客户端通过 ZK 获取节点列表，并按轮询策略选择端点。  
- **宕掉其中一个实例** 后，请求在短暂抖动后仍能落到存活实例上，而非长时间全部失败。

### 1.2 前置条件

- ZooKeeper 运行在 `127.0.0.1:2181`。  
- `bin/test.conf`、`bin/test_8001.conf` 中：  
  - `rpcserverip=127.0.0.1`  
  - `rpcserverport=8000 / 8001`  
  - `zookeeperip=127.0.0.1`、`zookeeperport=2181`  
  - `rpc_codec=msgpack`（两端一致）  
  - `enable_connection_pool=1`  
  - **未**设置 `skip_zookeeper_registration=1`。

### 1.3 步骤

**1）编译**

```bash
cd /home/zzz/Krpc
cmake --build build -j"$(nproc)"
```

**2）确认 ZK 存活**

```bash
echo ruok | nc 127.0.0.1 2181
```

预期：输出中包含 `imok`。

**3）终端 A：启动实例 8000**

```bash
cd /home/zzz/Krpc
unset LB_STATIC_ENDPOINTS
./bin/server -i ./bin/test.conf
```

**4）终端 B：启动实例 8001**

```bash
cd /home/zzz/Krpc
unset LB_STATIC_ENDPOINTS
./bin/server -i ./bin/test_8001.conf
```

**5）终端 C：在 ZK 中确认多实例已注册**

```bash
/usr/share/zookeeper/bin/zkCli.sh -server 127.0.0.1:2181
```

交互内执行：

```text
ls /UserServiceRpc/Login
quit
```

预期：看到类似 `"[127.0.0.1:8001, 127.0.0.1:8000]"` 的子节点列表，证明两个实例都已注册。

**6）终端 D：通过 ZK + 连接池发起多次调用**

```bash
cd /home/zzz/Krpc
unset LB_STATIC_ENDPOINTS
POOL_DEMO_MODE=new_channel POOL_DEMO_ITERATIONS=40 POOL_DEMO_SLEEP_MS=200 \
  ./bin/pool_demo -i ./bin/test.conf > /tmp/pool_zk.log 2>&1
```

查看摘要与关键日志：

```bash
grep -E "summary:|zk children|lb selected endpoint|connect server success|reuse pooled connection|fail" /tmp/pool_zk.log
```

理想情况：`summary: ok=40 fail=0`，并能看到 `lb selected endpoint` 在 8000 / 8001 之间轮换（实际关键字以当前版本日志为准）。

**7）停掉一个实例，验证自动退化**

在终端 B（8001）中 `Ctrl+C` 停止 `test_8001.conf` 对应的 server。

再次在终端 D 执行：

```bash
cd /home/zzz/Krpc
unset LB_STATIC_ENDPOINTS
POOL_DEMO_MODE=new_channel POOL_DEMO_ITERATIONS=40 POOL_DEMO_SLEEP_MS=200 \
  ./bin/pool_demo -i ./bin/test.conf > /tmp/pool_zk_after_kill.log 2>&1
```

```bash
grep -E "summary:|lb selected endpoint|fail" /tmp/pool_zk_after_kill.log
```

预期：

- `summary` 中绝大多数请求成功（理想为 `ok=40 fail=0`）。  
- 选端点日志最终只落到存活实例（例如只剩 `127.0.0.1:8000`）。

> **面试可讲要点**：  
> - 服务端在 ZK 下用 **临时子节点** 注册实例（会话在进程生命周期内保持）。  
> - 客户端按 ZK children + 轮询选端点，并在连接失败时结合 `lb_fail_cooldown_ms` 做短期“黑名单”，让流量自动偏向存活节点。

## 2. 心跳 + 空闲踢连接

### 2.1 场景目标

- 长时间空闲时，**连接仍然保持存活**（客户端心跳 + 服务端 Pong）。  
- 超过「允许连续心跳丢失次数 × 周期」后，服务端会**主动关闭长时间无活动的连接**。

### 2.2 基本配置

- `bin/test.conf` 中：  
  - `heartbeat_interval_ms`：例如 `5000`。  
  - `heartbeat_miss_limit`：例如 `3`。  
  - `rpc_timeout_ms`：默认 RPC 超时，心跳等待也沿用该超时。

### 2.3 步骤（概略）

1. 终端 A：`./bin/server -i ./bin/test.conf`。  
2. 终端 B：运行 `./bin/heartbeat_client -i ./bin/test.conf`，按文档设置 `HEARTBEAT_IDLE_SECONDS` 等环境变量，让客户端在一段时间内只依靠心跳保活。  
3. 观察服务端日志中是否持续看到 Ping/Pong 与连接仍处于 `connected` 状态。  
4. 停止客户端或人为拉长空闲时间，观察服务端在约 `interval × (miss_limit + 1)` 后输出 `closing idle connection` 并 `removeConnectionInLoop`。

> **面试可讲要点**：  
> - 心跳帧在 IO 线程快速处理，不进入业务线程池队列。  
> - 超时参数和 miss 次数可调，能在“不误伤正常长连接”与“及时回收僵尸连接”间权衡。

## 3. 注册中心不可用时的行为

### 3.1 场景目标

- 当 ZK 短暂不可用时，客户端应能**明确失败原因**，而不是静默挂起。  
+- 已有连接在短时内可继续使用（视实现与缓存策略而定）；本地压测路径可以退化到 **静态端点 `LB_STATIC_ENDPOINTS`**。

### 3.2 验证建议（仅需一次演示）

1. 在 ZK 正常时，使用静态端点压测（`LB_STATIC_ENDPOINTS=127.0.0.1:8000` + `bench_demo`），证明不依赖 ZK 也能完整跑通。  
2. 关闭 ZK 进程，再运行依赖 ZK 的 `pool_demo`，观察客户端日志中关于 `zookeeper ... Connection refused` 的错误；此时可解释：  
   - 「线上会把 ZK 作为发现平面，业务面则通过缓存与静态端点兜底」的设计思路。  

> **面试可讲要点**：  
> - Krpc 支持两条路径：**ZK 发现 + 多副本** 与 **环境变量静态端点**。  
> - ZK 不可用时，可以退回到静态列表；本项目的 demo 主要展示了这两条路径及各自的适用场景。
