## 1. 基准协议（Benchmark Protocol）

### 1.1 固定变量

- 服务器：
  - `bin/server -i bin/bench_local_<codec>.conf`
  - 端口：默认 `rpcserverport=8000`
  - 服务不依赖 ZK：配置里启用了 `skip_zookeeper_registration=1`（本地压测用）
- 客户端发现：
  - 通过 `LB_STATIC_ENDPOINTS=127.0.0.1:8000` 静态端点
- 压测脚本：
  - `scripts/run_bench_matrix.sh <protobuf|msgpack>`

### 1.2 维度矩阵

- `rpc_codec`：`protobuf` / `msgpack`（分别跑两轮）
- `BENCH_MODE`：`sync` / `async`
- `BENCH_CONN`：`keepalive` / `short`
- `BENCH_PAYLOAD_KB`：`0 / 1 / 64 / 256 / 1024`
  - 其中 `1024` 近似 1MB payload（`BenchClient` 内部按 KB 扩容）

### 1.3 本阶段使用的压测参数（建议在表格上方注明）

- `BENCH_CONCURRENCY`：`4`
- `BENCH_REQUESTS`：`10`（当前表格对应这组快速基准；如需更稳统计可改回 `100` 重跑）

### 1.4 成功/失败判定

- 以 `bench summary` 输出为准：
  - `success` / `fail`
  - 若 `fail > 0`，需要记录当次 case 的日志尾部（方便后续定位超时/断连）。
- 新版 `scripts/run_bench_matrix.sh` 增加了两道保护：
  - **服务就绪探测**：运行前会检查 `SERVER_IP:SERVER_PORT` 是否可连接（默认 `127.0.0.1:8000`）。
  - **无效样本拦截**：若某个 case 出现 `fail>0`（或 summary 解析失败），脚本会标记该 case 为无效；若无效 case 存在，脚本以非 0 退出并提示“结果不可用于 codec 对比”。

### 1.5 本轮排查结论（针对“codec 差异过大”）

- 关键问题并非 codec 算法本身，而是基准过程中存在 `connect error Connection refused`，导致大量 case 实际在“服务不可达”条件下完成，数据自然失真。  
- 这类样本会让 QPS、延迟呈现看似“差异巨大”的假象（本质是失败请求路径的统计），不能用于 Protobuf vs Msgpack 结论。  
- 修正策略：
  1. 保证服务端进程先启动并可连接；  
  2. 两轮仅切 codec，其余参数保持一致；  
  3. 脚本发现无效 case 时直接失败，避免把脏数据写进结论区。

### 3.3 两种序列化结果对比（是否符合常理）

#### 符合常理的部分

- **长连接（KA）普遍优于短连接（SH）**：两种协议里都基本成立：QPS 更高、延迟更低，符合「少握手、少建连」的预期。
- **payload 从 0/1KB 增到 1024KB 后，QPS 下降、延迟上升**：两种协议都有这个趋势，符合大包占用带宽与拷贝/序列化成本增加的预期。
- **async 多数情况下优于 sync**：多数组合里 async 的吞吐更高，也符合「异步不阻塞业务线程」的常见表现。

#### 需要警惕、不宜单独归因于「序列化格式」的部分

- **Protobuf 表中出现大量接近 100ms 的档位**（p95/p99 常在约 100～110ms，max 也常同值），更像被固定等待周期或调度粒度影响，而不是单纯「Protobuf 编码慢」。
- **Msgpack 在小包时相对 Protobuf 领先幅度很大**：若仅解释为「msgpack 比 protobuf 更快」，容易过度推断；更可能是两条实现路径（队列、线程、超时扫描、业务路径）存在额外差异，与编解码本身无关。
- **样本量偏小**：每格 `success=10`，统计稳定性不足，p95/p99 参考价值有限，更适合作为「矩阵占位」而非「精确对比结论」。

#### 结论（可复述）

- 这两张表**不能直接**推出「msgpack 一定全面优于 protobuf」；当前数据更像是**整条链路**（含实现与测量）的综合结果，其中**非序列化因素**可能占主导。
- 若要在「公平对比两种序列化」上立论，需要**控制变量**并**放大样本**（见下）。

#### 建议后续补一轮（更有说服力）

- 每组合请求数至少到 **1k～10k**，再汇报 p50/p95/p99 与错误率。
- 区分 **空业务**（handler 只做 echo）与 **真实业务** 两组，避免业务耗时淹没编解码差异。
- 确保两种 codec 下 **连接策略、线程模型、超时参数** 一致。
- 若条件允许，可额外记录 **排队/网络/业务** 分段耗时，便于解释为何出现 ~100ms 档位。
