# Krpc 工程化与稳定性完善计划（第二版）

> 面向暑期实习与后端岗位面试：重点不是「功能列表有多长」，而是**能否像真实线上服务一样思考**——需求边界、失败模式、可观测性、变更风险控制与持续验证。  
> 本文与 [`feature_summary.md`](feature_summary.md) 互补：后者记录「已经做了什么」，本文回答「从工程视角还缺什么、按什么顺序补」。

---

## 1. 面试官想看的「工程化」是什么

面试官通常用项目考察你是否具备**可迁移的工程习惯**，而不是是否手写过一个 RPC。可概括为五条，每条都应有**仓库里的证据**（文档、脚本、测试、配置或演示），而不是口头宣称。

| 维度 | 含义 | 反面（容易被追问穿） |
|------|------|----------------------|
| **需求与边界** | 明确适用场景（延迟/吞吐/部署形态），知道什么不做 | 「高性能」但无指标、无对比基线 |
| **失败是常态** | 超时、断连、半开连接、后端过载、依赖（如 ZK）抖动 | 只演示 happy path |
| **可观测性** | 日志可关联、指标可聚合、关键路径可解释 | 只有 cout/glog 散落，无结构化字段 |
| **变更可信** | 自动化构建与测试、关键路径有回归 | 手工点一点「能跑」 |
| **运维与成本** | 配置、限流、容量、升级与回滚有思路 | 写死 IP、无超时分级 |

你的 Krpc 已有异步、连接池、负载均衡、心跳、Metrics 等**很好的骨架**；差距主要在：**把这些能力组织成「可证明的工程质量」**（基线、SLO 叙事、故障演练、测试与 CI）。

## 2. 稳定性：实际场景里「必须交代」的几件事

下面每一项都是工业界 RPC/网关常见考点，不要求你全部实现，但**选 2～3 个做深**，比再堆十个 demo 更有说服力。

### 2.1 明确 SLO 与压测叙事（先有尺子）

- **目标**：能说清「在什么条件下」的数字——单机 loopback 还是双机、payload、并发、codec、是否连接池、是否跨线程池队列。  
- **做法**：固定一份「基准协议」（硬件、内核参数若可则记录、`BENCH_*` 环境变量、`rpc_codec`、长/短连接），输出**表格**：QPS、p50/p95/p99、错误率；大包（如 64KB～1MB）至少一行，避免「只有几十字节」的观感。  
- **工程点**：这是**需求边界**与**可复现性**，体现你对性能数字的严肃性。

### 2.2 失败模式清单（Failure modes）

至少能口头 + 文档列出，并**选几条用现有或少量扩展代码演示**：

| 场景 | 期望行为 | 与 Krpc 的关联 |
|------|----------|----------------|
| 单次调用超时 | 客户端失败可判定，资源释放，不泄漏 fd/ pending | `Krpccontroller`、异步 TimeoutManager |
| 连接断开 / 心跳失败 | 重连、未决请求失败路径一致 | 心跳 + `FailPending` 类逻辑 |
| 后端单点宕机 | 轮询试其他节点、失败冷却 | `lb_fail_cooldown_ms`、静态多端口演示 |
| 服务端过载 | 队列满、背压、拒绝或降级策略可讲清 | `provider_queue_capacity`、worker 池 |
| 注册中心不可用 | 发现失败 vs 已有连接是否可继续 | ZK 与缓存 TTL、静态端点 `LB_STATIC_ENDPOINTS` |

**工程点**：说明你知道线上**不是调通就行**，而是「坏了以后系统处于什么状态」。

### 2.3 可观测性分层（Logs / Metrics / Traces 的「最小可用」）

- **Logs**：关键字段一致——至少 `request_id`、服务名、方法名；若扩展 **`trace_id`**（见下文），同一条链在客户端与服务端日志可对齐。  
- **Metrics**：已有 Prometheus 文本导出时，面试可讲 histogram/summary 与错误率；可补充「按错误类型计数」比只有 QPS 更贴近稳定性。  
- **Traces**：不必上全套 Jaeger；**请求头携带 trace_id + 日志打印**即可讲清「上下文传播」与后续接入 OpenTelemetry 的路径。

### 2.4 测试与 CI：把「我保证」变成「机器保证」

- **单元/协议测试**：帧边界、粘包、header 解析、`request_id` 匹配（不必依赖 Muduo 的轻量测试）。  
- **集成测试**：可选，需 ZK/多进程时可用脚本 + 固定端口或容器。  
- **CI**：提交即 `cmake` + `build` + `ctest`；条件允许时加 **ASan** 构建类型跑示例。  

**工程点**：体现**回归意识**与**团队协作习惯**。

### 2.5 配置、安全与上线（点到为止即可加分）

- 敏感信息不进仓库；配置项含义表（你已有大量 conf，可整理一页「参数手册」）。  
- TLS、鉴权若未做，**明确写「未做及原因」**比回避更好；可写「接口预留点」。

## 4. 分阶段路线图（建议 3～6 周，可裁剪）

### 阶段 A：度量与叙事（1 周）

- 定「基准协议」，跑满 payload × codec × 同步/异步 × 连接模式，写入 [`docs/benchmarks.md`](benchmarks.md)（若尚无则新建）。  
- README 或 docs 中用**一段话**说明适用场景与**非目标**（例如：教学用 RPC，未实现加密与鉴权）。

### 阶段 B：可信与自动化（1～2 周）

- 引入单元测试框架，覆盖协议与关键边界；接 GitHub Actions / GitLab CI。  
- 可选：Sanitizer 构建跑通主路径示例。

### 阶段 C：稳定性「可见」（1～2 周）

- （已完成）**trace_id 贯穿日志**：见 [`深挖_trace_id_日志传播.md`](深挖_trace_id_日志传播.md)，覆盖 `RpcHeader.trace_id`、controller reset 行为及日志对齐示例。  
- （已完成）**ZK 多实例 + 故障演练**：见 [`故障演练_稳定性验证.md`](故障演练_稳定性验证.md)，包括 ZK 发现 + 多副本、单实例宕机切换、心跳与空闲踢连接等脚本与预期现象。  
- （可选）**熔断/重试策略**（与现有失败冷却衔接），或更细粒度的错误类 metrics；当前版本已通过 Metrics 导出全局与按方法维度的成功/失败与 fail_rate，可用于基础稳定性叙事。

### 阶段 D：面试材料（持续）

- 一页架构图（客户端线程模型 → 帧 → Muduo → 线程池 → ZK）。  
- 「个人贡献」3～5 条：每条对应**问题 → 设计 → 验证方式**。  
- 准备与 gRPC/brpc 的对比：**差异 + 若继续演进会改哪里**。

## 5. 简历与答辩：如何把工程化「说透」

- **不要只报 QPS**：加上条件（payload、并发、loopback）、以及 p99 与错误率。  
- **主动讲失败**：「连接断开时 pending 如何清理」「队列满时策略是什么」。  
- **把 CI/测试说成质量门禁**：「合并前自动跑协议回归」。  
- **承认边界**：未做 TLS 时，说明原因与扩展点——比含糊其辞更像工程师。
